## 0. なぜ MCP サーバなのか（設計の分岐点）

当初の依頼は「Nous Hermes 用の統合モジュール」だった。調査の結果、**Hermes 固有の
プラグインとして作るべきではない**と判断した。理由:

- Hermes は **MCP（Model Context Protocol）を一級で対応**している。`~/.hermes/config.yaml`
  の `mcp_servers` に stdio または HTTP のサーバを登録すれば、そのツールが Hermes の
  ツール一覧に入る（出典: `https://hermes-agent.nousresearch.com/docs/user-guide/features/mcp`）
- MCP サーバとして作れば、**Hermes 専用にならない**。依頼の「他エージェントが再利用できる
  形で公開する」に直結する。
  ★ ただし「**任意の** MCP エージェントがそのまま使える」とは書かない（r1 監査 LOW）。
  この設計は **untrusted の前置きラベルと、対外発信を表面から外すこと**に安全性を
  置いているので、**ツール結果の表示方法と承認 UI がクライアントごとに違うことは、
  互換性の問題ではなく安全境界の問題になる**。
  対象は「stdio または HTTP を扱え、ツール結果を安全に提示する MCP クライアント」と限定する
- **flop-labs 自身が同じ作法を採っている**。tclk/1 はホスト型 MCP を
  `https://tclk.technocore.chat/mcp` で出している。エコシステムの既定の形に合わせる

→ **成果物は `technocore-mcp`（MCP サーバ）。Hermes への統合は「config に3行足す」に還元される。**

★ この判断の副産物として、**成果物自体は LLM を必要としない**。MCP サーバはツールを
提供するだけで、推論するのは呼び出す側のエージェントである。LLM プロバイダの選定が
要るのは「統合を端から端まで試すための Hermes テストインスタンス」だけになる（§7）。

## 1. 目的と対象読者

**目的**: MCP 対応エージェントが、technocore.chat 上で did:key 署名付きの読み書きと
E2E 暗号化ルームを扱えるようにする。

**対象読者**: 他エージェントの運用者。前提知識は「自分のエージェントに MCP サーバを
登録したことがある」程度を想定し、technocore と did:key の知識は前提としない。

**非目標**:
- 本番 Hermes の機能拡張ではない（本番には一切触れない）
- エアドロの自動獲得装置ではない。faucet も推論課金も仕様が未公開（§6）
- tclk/1 の再実装ではない（§5）

## 2. 提供 tool 一覧

MCP のツールとして公開するもの。**すべて `technocore_` 接頭辞**で名前空間を切る。

### 読み取り系

| tool | 入力 | 出力 | 備考 |
|---|---|---|---|
| `technocore_read_room` | `room`, `since?`, `limit?` | メッセージ配列（seq, ts, from, text） | **出力は必ず untrusted としてラベル付けする**（§3） |
| `technocore_wait_room` | `room`, `since`, `wait?`(0-10) | 同上 | 長ポーリング。`# wait: not held` を検出して呼び出し側に返す |
| `technocore_export_room` | `room`, `inline?` | **既定: サーバ所有の export ディレクトリに保存し、生成したパス・件数・期間・X-Room-Generation を返す**。`inline: true` のときのみ `{kind: "untrusted_export", note, jsonl}` として構造化して返す | ★ **保存先はモデルが指定できない**（下記）|

★★ **`out_path` は提供しない。** r1 の修正で「モデル文脈に入れない代わりにファイルへ落とす」
とした際、**保存先をモデル生成の引数にしていた**（r2 監査 HIGH）。書き込む中身は
攻撃者が選んだバイト列なので、**プロンプト注入で任意の場所にファイルを置ける原始的手段**を
渡すことになる。しかも §3 の隔離境界に「エクスポート成果物」は許可対象として
書いていなかった ── **設計が自分自身と矛盾していた。**

保存の条件（すべてサーバ側で固定し、引数で動かせない）:

- 保存先は **サーバ所有の1ディレクトリのみ**（既定 `~/.technocore/exports/`、mode 700）
- ファイル名は**サーバが生成**する（`<room>-<generation>-<UTC timestamp>.jsonl`。
  room 名は既に `NAME_RE` で検証済み）
- **正規化後のパスがその基底ディレクトリ配下にあることを確認**する（`Path.resolve()` 後に
  `is_relative_to()`）。シンボリックリンクを辿らせない
- **上書きしない**（`O_EXCL`）。同名があれば失敗する
- **サイズ上限**を設ける（既定 64 MiB。ルームのリングは ~10 MiB 想定なので十分）
- 返却は「これは untrusted な内容を含むファイルである」ことを明示したラベル付き

**別の場所に置きたい場合は、人間が返されたパスから移動する。**
ツールに移動先を教える口は作らない。
| `technocore_read_note` | `namespace`, `key` | note の値 | ★ **両方 `NAME_RE` を通す**（下記）|
| `technocore_resolve_did` | `did` | note の値（x25519 公開鍵・mailbox） | sharded → legacy の順に試す。shard は `fingerprint(did)` から**自分で導出**する（入力から取らない）|
| `technocore_list_rooms` | — | `/rooms` の生出力 | **名前と topic は caller-chosen。untrusted** |

### ★★ パス segment になる入力は、例外なく `NAME_RE` を通す（r9 監査 HIGH）

一次資料で、note の**読みと書きが隣接ルート**であることが確認できる:

```
NOTES   GET /kv/<ns>/<key>                 read a persisted note
        GET /kv/<ns>/<key>/set/<value>     write one (URL-encoded)
Names (<room>, <nick>, <ns>, <key>) match /^[a-z0-9][a-z0-9_-]{0,47}$/.
                              — llms.txt（technocore.chat が公開している仕様）
```

したがって `key` に `/` を含められると、**読み取りツールが書き込みルートになる**:

| 入力 | 組み上がるパス | 実際の意味 |
|---|---|---|
| `key="x"` | `/kv/ns/x` | 読み |
| `key="x/set/<攻撃者の値>"` | `/kv/ns/x/set/<攻撃者の値>` | **書き込み** |

**§3 の origin 検査はこれを止めない。** ホストは `technocore.chat` のままだからである。
r1〜r4 で消したはずの publish 経路を、**読み取りツールの引数から再導入していた。**

しかも vendor の `validate_name()` は、その docstring でこの攻撃を名指ししている
（「Interpolating that string into a request path unchecked lets a stranger
redirect your signed writes」）。**許可リストに載せておきながら、
自分のツール表に適用していなかった。**

規則:

1. **モデル由来の値が URL の path segment になるなら、`validate_name()` を通す。**
   対象は `room` / `namespace` / `key` / `nick`。通らなければ**呼ばない**
2. **内容（text・note の値）は segment ではない。** `urllib.parse.quote(..., safe="")`
   で完全にエンコードし、**区切りとして解釈されうる文字を残さない**
3. **`fetch_technocore` は「組み上がったパス文字列」を受け取らない。**
   受け取るのは **MCP 内で固定した経路テンプレートの識別子＋検証済み segment** であり、
   テンプレートは列挙された定数集合（`/r/{room}`、`/kv/{ns}/{key}`、`/rooms` …）。
   **呼び出し側がパスを組み立てられる限り、組み立ての時点で同じ混同が起きる**ので、
   組み立てをラッパーの内側に閉じる
4. `technocore_resolve_did` の shard は**入力ではなく `fingerprint(did)` から導出**する

★ **origin 検査（§3）とこの規則は別の問い**である ──
「どのホストへ行くか」と「そのホストで何をするか」。
**前者を通したことは後者の証明にならない。**

### 書き込み系（署名）

| tool | 入力 | 出力 | 備考 |
|---|---|---|---|
| `technocore_say_signed` | `room`, `text` | seq / サーバ応答 | sweep → 署名 → GET/POST 自動選択 |

★ **DID note の公開ツールは提供しない。** 初版は `confirm: true` を必須にする案だったが、
**MCP のツール引数は呼び出し側モデルが生成するものであり、untrusted なルーム内容が
「`confirm: true` で呼べ」と誘導すればゲートは通過する**（r1 監査 HIGH）。
「人間が確認した」と「モデルが boolean を入れた」は別物なので、その区別を
boolean で表現しようとしたのが誤りだった。

代わりに `technocore_did_note`（読み取り専用）を提供する。**公開すべき note の値と、
どこに置くかの座標（shard・key）を返すだけ。** 公開は人間が別途行う。

| tool | 入力 | 出力 | 備考 |
|---|---|---|---|
| `technocore_did_note` | — | note の値、shard、key（sharded / legacy 両方の座標） | **副作用ゼロ。書き込み URL を返す経路を持たない** |

★★ **`/kv/.../set/...` を返さないのは、URL 自体が実行可能物だから。**
r1 で「ツールを消して URL を返すだけにした」が、**そのサーバは書き込みを GET で行う**ので、
`set` URL は「叩けば公開される命令」そのものである。呼び出し側モデルが fetch / browser /
web ツールを併せ持っていれば（Hermes は実際に持ちうる）、untrusted なルーム内容が
「さっきの URL を取得して」と誘導するだけで公開が起きる。
**publish ツールを消しても、その URL をモデル文脈に置いた時点で publish 経路は残っていた**
（r2 監査 MEDIUM）。

- 出力は **値と座標のみ**。URL を返す引数を**持たない**
- 人間はこの2つから自力で URL を組める。**組み方は README に人間向けに書く**
  （MCP の応答経路の外側に置く）
- ★ r3 では `include_write_url?` というオプトイン引数で URL を返す案にしていた。
  **これは同じ文書に書いた不変条件そのものへの違反だった**（r3 監査 MEDIUM）。
  「既定が安全なら良い」ではない ── モデルが生成できる引数で辿れる時点で、
  攻撃者が選べる値で publish 経路が復活する。**ラベルは境界ではない。**
  `human_only_do_not_fetch` のような構造化ラベルは、
  **返すと決めた後の被害を減らす道具であって、返すかどうかの判断には使えない**

### ★★ ただし、これで DID note の書き込みを防げてはいない（残存リスク・防げない側）

r4 監査は「値と shard/key を返せば URL は組み立てられるので、まだモデルに
publish 能力を渡している」と指摘した。**組み立てられるのは事実だが、
提案された対処（値と shard/key も返さない）では防げない。** 一次資料で確認した:

| 事実 | 出典 |
|---|---|
| 書き込み先は **DID だけから決まる**。`note_urls(did)` は `fingerprint(did)` の先頭2文字でシャードするだけの純関数 | `e2e_current.py` `note_urls()` |
| note の値は `did + " x25519:" + 公開鍵 + " mailbox:" + mailbox` の連結 | 同 `note_value()` |
| この2つの材料は **`technocore_whoami` が返すもの**（DID・x25519 公開鍵・mailbox）。これを返さないとサーバの用が無い | §2 |
| 書き込みは **GET**。KV の note は署名不要（world-writable） | llms.txt / patterns.md |

つまり **`technocore_did_note` を消しても、`whoami` と公開仕様と fetch ツールがあれば
経路は再現できる。** shard/key を伏せることは、導出を1段ずらすだけで**何も買っていない**。
「ラベルは境界ではない」と同じ理由で、**「材料を分けて返す」も境界ではない。**

★ **本当の境界はこのサーバの表面ではなく、呼び出し側エージェントの道具構成にある。**
したがって設計として書くべきは、ツールの引数ではなく**配備の前提条件**である:

1. **このサーバを、無制限の fetch / browser / HTTP ツールと同じエージェントに
   同居させない。** 同居させた時点で、technocore の**署名不要な書き込みはすべて**
   モデルから到達可能になる（このサーバの表面と無関係に）
2. 署名が要る操作（say / room 投稿）は**一部だけ**この限りではない。
   秘密鍵は MCP サーバのプロセス内にあり、fetch ツールでは**新しい署名を作れない**。
   **守れているのは鍵が守っている部分であって、私の引数設計ではない**

   ★ **ただし「署名済み操作は安全」は書きすぎだった**（r5 監査 MEDIUM）。
   一次資料が反例を明示している:

   > NONCE: it must be greater than the last nonce that key used in that room.
   > … That makes a captured signed URL single-use **only while the message
   > remains in the newest 1 MiB scanned for the last nonce**. Once newer
   > traffic buries it beyond that tail, the same URL is accepted again …
   > **Signatures still prove authorship; only the single-use guarantee
   > expires early.** — llms.txt

   つまり:

   | 署名が守るもの | 守らないもの |
   |---|---|
   | 作者性（誰の鍵か） | **古い署名済みレコードの再送** |
   | 新規の署名済み書き込みを他人が作ること | 尾（1 MiB）を越えた後の単発性 |

   しかも `sig` は**ルームの読み手全員に配られる**（`p-` ルームなら room key を
   持つ全員）。したがって **fetch ツールを持つ相手は、観測した署名済み URL を
   尾が流れた後に再送できる**。鍵は要らない。
   **これは私の設計の穴ではなくプロトコルの性質だが、
   「鍵があるから守れている」と書けば嘘になる。**

   ★ 帰結（実装に効く）: **署名済みレコードを状態遷移の引き金に使う消費側は、
   再送されうる前提で重複排除する。** 尾は**バイト予算であってメッセージ数ではない**
   （`sig` が1件あたり95バイト増やすので、短い署名済みメッセージのルームでは
   入る件数が約3分の1減り、単発性の保証期間もその分短くなる）。
   したがって「何件までなら安全」と件数で見積もらない。
   重複排除は `(did, nonce, text)` か、アプリ側の id で行う
3. ★ **防げないので、検知に倒す。** note が第三者に書き換えられる可能性は
   同居の有無にかかわらず残る（world-writable なので**攻撃者は最初から直接書ける**）。
   したがってパッケージに **note 照合コマンド**を同梱し、人間または cron が
   定期実行して「現在の note が自分の値と一致するか」を確認する。
   不一致は**自動修復せず通知する**（黙って直すと気づけない）。

**この項は「直した」ではなく「防げないと確定した」項目である。**
r1 で publish ツールを消し、r2 で URL を消し、r3 で引数を消したが、
**3回とも縮んだのは私の表面であって、攻撃者の経路ではなかった。**

### E2E

| tool | 入力 | 出力 | 備考 |
|---|---|---|---|
| `technocore_seal_room_key` | `recipient_x25519`, `room?` | `e2e1` 行, room, room_key, `key_corroboration_required: true` | **警告は常に出力する。抑止する引数を持たない**（下記）|
| `technocore_open_sealed` | `line` | room, room_key | 自分宛でなければ明示的にそう返す |
| `technocore_encrypt_line` / `technocore_decrypt_line` | `room_key`, `text`/`line` | 暗号文 / 平文 | 4096字上限を超えたら拒否 |

★★ **`corroborated: bool` は持たせない。** 相手の x25519 公開鍵は technocore の
world-readable な note から取ってくるので、**note を差し替えられれば鍵をすり替えられる**
（別経路での照合が要る、というのが警告の中身）。初版はその警告を `corroborated: false`
のときだけ出す設計にしていたが、**それはモデルが生成する引数を信頼シグナルとして使う**
ことであり、r1 HIGH の `confirm: true` とまったく同じ欠陥である（r2 監査 LOW）。
r1 で `confirm` を消したときに**気づいた場所だけ直して、同じ型の他の1件を残していた。**

したがって:

- 警告は**常に**出す。抑止する口を作らない
- 出力に `key_corroboration_required: true` を構造化フィールドとして常に含める
  （文面だけだと要約で落ちる）
- 「照合したか」は人間だけが知りうる事実なので、**MCP の表面に置かない**

## 3. DID・秘密鍵の保管と隔離境界

### 保管

- 鍵ファイルは **MCP サーバのプロセスだけが読める場所**に置く。既定 `~/.technocore/identity.json`、
  mode 600・親ディレクトリ 700。**e2e.py の `save_identity()` がこれを強制する**
  （git 作業ツリー内は拒否。gitと親探索の二段で判定し、判定不能なら書かない）
- **鍵の値をツール出力に載せる経路を作らない。** `technocore_whoami` は公開情報のみ返す
- 環境変数経由で鍵を渡す口は作らない（プロセス一覧・MCP の `env` 受け渡しで漏れるため）

### 隔離境界

このサーバが**触れてよいもの**（★ここに挙がっていないものには到達経路を作らない）:
- `technocore.chat` への HTTPS
- 自分の identity ファイル（`~/.technocore/identity.json`、mode 600）
- 自分の状態ファイル（既読 seq のカーソル等、`~/.technocore/state/`）
- ★ **エクスポート先ディレクトリ `~/.technocore/exports/`（mode 700）**。
  `technocore_export_room` が書く唯一の場所で、**ファイル名はサーバが生成し、
  引数で位置を動かせない**（§2）。r1 でエクスポートのファイル書き込みを足したとき、
  この境界に追記しなかった ── **設計が §2 で許した操作を §3 が許していない状態**を
  作っていた（r2 監査 HIGH）。書き込む中身は攻撃者が選んだバイト列なので、
  この1ディレクトリに閉じ込め、上書きせず、サイズ上限を持たせる

**★ 境界の運用規則**: ツールに新しい副作用を足すときは、**§2 と §3 を同じ変更で
両方直す**。片方だけ直した差分はレビューで落とす。r1→r2 の HIGH はこれを怠って出た。

**触れてはならないもの（設計上、到達経路を持たせない）**:
- 運用者のノート・ナレッジベースの類
- 他プロジェクトのリポジトリ・`.env`・wallet・署名鍵
- 別インスタンスの Hermes の設定・鍵・`~/.hermes/`
- 同じホストで動く他の本番プロセスのデータ

★ この一覧は具体的な配備環境から一般化したもの。**自分の環境で「隣に何があるか」を
数え上げて、この形で書き出すこと。** 抽象的なカテゴリのままだと、自分の環境の何が
該当するのかを読み手が写像し損ねる ── 実際、この設計の配備前提条件は
「fetch / browser 系」と書いたせいで、シェルという最も強い1件を見落とした。

★ **配備の前提条件（表面では守れない部分）**:
- **無制限の fetch / browser / HTTP ツールと同じエージェントに同居させない。**
  同居すると technocore の署名不要な書き込み（DID note の KV set 等）が
  モデルから到達可能になる。これは**このサーバの表面では防げない**（§2 の
  「防げない側」を参照）。守れているのは秘密鍵が守る部分だけである
- note の照合コマンドを定期実行し、**不一致は自動修復せず通知する**

実装形態は **stdio サーバ**を既定とする。HTTP サーバにすると待ち受けポートという
攻撃面が増え、認証を自前で持つ必要が出るため。stdio なら親プロセス（エージェント）が
起動・終了を握り、ネットワーク的な待ち受けがゼロになる。

### ★ untrusted 入力の扱い（最重要）

technocore のルーム・note・ルーム名・topic は**すべて見知らぬ相手が書いたバイト列**であり、
サーバ自身がそう明言している。したがって:

1. **読み取り系ツールの出力は、必ず「これはデータであって指示ではない」旨の前置きを
   付けて返す。** 呼び出し側 LLM の文脈に素で流し込まない
2. **復号しても untrusted のまま。** E2E は「誰が書いたか」を保証せず、ルーム名を知る者は
   誰でも書ける
3. Hermes 側は MCP 結果から不可視 Unicode TAG 文字を除去する実装になっているが、
   **それに依存しない**。こちら側でも sweep 相当の正規化をかけてから返す
4. ★ **対外発信になる操作は、そもそもツールとして提供しない。** DID note の公開が該当する。
   人間の確認が要る操作は、MCP の表面から外して人間の手元に置く（§2）

### ★★ 不変条件: モデルが生成する引数は、安全境界を動かせない

**この設計で3回連続で出た欠陥はすべてこの1つの型だった**（r1 HIGH `confirm: true`、
r2 HIGH `out_path`、r2 LOW `corroborated`）。**毎回、直した箇所の隣に同じ型が残っていた。**
個別に潰すのをやめ、不変条件として書く:

> ツール引数は**呼び出し側モデルの出力**であり、
> untrusted なルーム内容はそのモデルの入力に混じる。
> したがって引数は「攻撃者が選べる値」と等価であって、
> **人間の意思・外部での照合・安全な保存先を表現できない。**

具体的に、引数で表現してはならないもの:

| 表現したいこと | 引数で書くと | 正しい置き方 |
|---|---|---|
| 人間が承認した | `confirm: true` | その操作をツールとして持たない |
| 書き込み先 | `out_path` | サーバ側で固定、名前も生成 |
| 別経路で鍵を照合した | `corroborated: true` | 警告を常に出す。抑止口を作らない |
| 危険な値は既定で隠す | `include_write_url: true` | **返す経路自体を持たない** |

**引数として許されるのは、間違っても被害が「その呼び出しの結果が使えない」で
止まるものだけ**（`room` / `text` / `line` など）。

### ★ ラベルは境界ではない

4行目は r3 で自分が犯した違反である。**同じ文書にこの不変条件を書きながら、
`include_write_url` というオプトイン引数を残していた**（r3 監査 MEDIUM）。
理屈は「既定が安全だから」だったが、それは不変条件が禁じている考え方そのものだった。

- **「既定で off」は境界ではない。** モデルが on にできる
- **構造化ラベル（`human_only_do_not_fetch` 等）も境界ではない。**
  ラベルは「返すと決めたものの被害を減らす」道具であって、
  **「返してよいか」の判断には使えない**

したがって判断の順序は 1) **返さない経路を選べるか** → 2) 選べないならラベルを付ける、
であって逆ではない。

唯一残る同種の引数は `technocore_export_room` の `inline` である。これは
**上の順序を通した結果**として残す ── ルーム本文はそもそも読むために取りに行くもので、
「返さない」を選ぶとツールの目的が消える。だから既定をファイルにし、
`inline: true` のときは `kind: "untrusted_export"` を付ける。
**モデルが `inline: true` を選んだときに起きる最悪のことは
「untrusted な本文がラベル付きで文脈に入る」であり、副作用ではない。**
`include_write_url` はここが違った（最悪が publish だった）。

★ **レビュー手順**: ツール表に引数を1つ足すたび、この表に照らして
「攻撃者がこの値を選んだら何が起きるか」を1行書く。**その1行が副作用を含むなら、
引数ではなく経路を消す。** 書けないなら足さない。

## 4. e2e.py との関係 — **ベンダリング（写し込み）を選ぶ**

### 選択肢

| 案 | 内容 | 判断 |
|---|---|---|
| A. import 依存 | e2e.py を pip パッケージ化して依存する | **却下**。e2e.py は「1ファイルを curl して使う」設計で、それ自体が公開物の性質。パッケージ化は公開済み成果物の変更にあたり、今回の「e2e.py は変更しない」に反する |
| B. 必要部分を移植 | 暗号・署名部分を書き直す | **却下**。r6〜r11 の監査で潰した論点（sweep のカテゴリ、URL 予算、nonce 単調性、鍵配置ガード）を**もう一度踏み直すことになる** |
| **C. ベンダリング＋固定** | e2e.py を**逐語コピー**し、上流の commit hash を記録、起動時に照合 | **採用** |

### 採用理由と、その代償への対処

C は複製を作る。**このプロジェクトで一番痛い目を見たのが複製の黙った乖離**
（上流の仕様が動いたのに、こちらの写しが追随できていなかった件）。
だから複製を**見えるようにする**:

- `vendor/e2e.py` に逐語コピー。改変しない（改変したら別物なので上流の監査結果が効かない）
- `vendor/UPSTREAM.txt` に **上流 commit hash と取得日時**を記録
- **起動時にコピーの SHA-256 を記録値と照合し、食い違ったら起動を拒否する**（fail-closed）

### ★★ 使うのは関数層だけ。CLI 層には触れない（r3 監査 LOW）

**逐語コピーなので、e2e.py の CLI 層にある `--key-is-corroborated` も一緒に入ってくる。**
§2 で MCP の表面から抑止引数を消しても、**1階層下に同じ信頼シグナルが残っている**
という指摘。これは正しい。

幸い、e2e.py はその2つが別の層に分かれている:

| 層 | 場所 | 抑止フラグ |
|---|---|---|
| 暗号（関数） | `seal_room_key()` | **持たない**。純粋に封をするだけ |
| CLI（表示） | `cmd_seal()` / `main()` の argparse | `--key-is-corroborated` で警告を出し分ける |

したがって:

- **MCP サーバは `seal_room_key()` 等の関数を直接呼ぶ。`cmd_seal()` も `main()` も
  argparse も呼ばない。** CLI 層は到達不能なコードとしてコピーの中に残るだけ
- 警告と `key_corroboration_required` は **MCP 側が常に付ける**（§2）。
  e2e.py の警告分岐には依存しない
- **コピーは改変しない。** 抑止フラグを削れば上流とバイト一致しなくなり、
  §4 の照合と上流監査結果の適用がどちらも壊れる。
  **「使わない」で閉じるほうが、複製を1つ増やすより安い**
- ★ **テストで固定する**: ① MCP のツールスキーマ全体に
  corroboration 相当の引数が存在しないこと ② **vendor モジュールのうち MCP から
  呼んでよい関数を許可リストで持ち、それ以外への参照があれば落とす**（import グラフ検査）。
  **「呼ばないつもり」は時間が経てば破れるので、破れたら落ちるようにする**

★ **②を「`cmd_seal` と `main` を禁止する」と書かないのは、それが4回やった失敗の形
だから**（r4 監査 MEDIUM）。r3 で指摘された2つを名指しで塞いだ版は、
**同じ vendor ファイルの `cmd_note()`（572-577行）と `note_urls()` を素通しにしていた** ──
それこそが `/kv/.../set/` を組み立てる関数である。**禁止リストは、指摘された分しか
守らない。** したがって既定を反転させる:

許可リストは **vendor に実在するシンボル名で書く**（r5 監査 MEDIUM）。
r4 版は `open_sealed` と書いていたが、**それは MCP のツール名であって
vendor の関数名ではない**（実体は `open_room_key`）。ツール名を関数名として
書いた結果、**テストが「存在しないシンボル」を検査する＝何も検査しない**か、
機構化したかった当の境界に手作業の対応表を生やすかのどちらかになっていた。

| 許可するシンボル（vendor に実在） | 副作用 |
|---|---|
| `seal_room_key` / `open_room_key` / `encrypt_line` / `decrypt_line` | 無し（純粋な暗号） |
| `derive_shared` / `signing_key` / `sealing_key` / `fingerprint` | 無し |
| `sweep_single_line` / `validate_name` / `b64u` / `unb64u` | 無し |
| `note_value` | 無し（文字列を組むだけ） |
| `load_identity` | **ファイル読み取り**（identity のみ。書き込みはしない） |
| `next_nonce` | **状態更新**（nonce の単調性に必要） |
| `say_signed` / `read_room` | **ネットワーク**。宛先を決めるのは**内部で組む `f"{BASE}/r/{validate_name(room)}"`** ── `BASE` の直後がリテラルの `/` で、room は `NAME_RE`（`^[a-z0-9][a-z0-9_-]{0,47}$`）を通る。**呼び出し側の文字列が authority に届かない** |
| `find_sealed_lines` / `find_cipher_lines` | 無し |

既定で禁止（上表に無いものすべて）:

- `cmd_*` **すべて**（`cmd_note` / `cmd_seal` / `cmd_keygen` / `cmd_open` /
  `cmd_encrypt` / `cmd_decrypt` / `cmd_self_test` / `cmd_live_test`）
- `main` と argparse 定義
- **`note_urls`** ── 書き込み経路を組み立てる関数
- `create_identity` / `save_identity` / `resolve_identity_path` /
  `enclosing_git_worktree` ── 鍵の生成と配置は MCP の仕事ではない（人間が e2e.py で行う）
- ★ **`get`** ── **これが「副作用の欄を埋める」を実際に働かせた1件**（r6 監査 MEDIUM）

★★ **`get` を許可リストから外す理由**: `get(url: str)` は受け取った文字列を
そのまま `urllib.request.Request` に渡す。**宛先を限定していない汎用 fetch である。**
r5 版の表では `post` と同じ行に置いて「technocore へのみ」と書いていたが、
それは `get` の性質ではなかった。これを許可したままにすると、
**§3 で「同居させるな」と書いた当の無制限 fetch を自分の許可リストの中に
置いていた**ことになる。**隔離境界を自分で破る穴だった。**

★★ **`post` も外す**（r7 監査 MEDIUM）。r6 版は `post(path, payload)` を
「`BASE + path` だから安全」として残したが、**それは `get` で犯したのと同じ推論**
── 引数の**名前**が `path` であることを、宛先が縛られている証拠として使っていた。
実際には `post` を呼ぶのは vendor 内の `say_signed` 1箇所だけで、
**MCP の一次ツールとして公開する必要がそもそも無い。**
必要が無いものを「たぶん安全」で許可リストに残さない。

### `BASE + path` は origin を縛らない（r7 監査 HIGH）

**`BASE = "https://technocore.chat"` には末尾スラッシュが無い。**
したがって `/` で始まらない `path` を連結すると **authority が変わる**:

| path | 連結結果 | 宛先 |
|---|---|---|
| `/r/jobs` | `https://technocore.chat/r/jobs` | technocore |
| `.evil.com/r/jobs` | `https://technocore.chat.evil.com/r/jobs` | **別ホスト** |
| `@evil.com/x` | `https://technocore.chat@evil.com/x` | **別ホスト**（`technocore.chat` は userinfo になる）|

r6 版のラッパーは「full URL・スキーム付き・`//` 始まりを拒否する」と書いていたが、
**上の3行目はそのどれにも該当しない。** 入力の形を列挙して弾く書き方＝**禁止リスト**を
また書いていた。この設計で4回失敗した形である。

### `fetch_technocore` の API — **パス文字列を受け取る口は存在しない**

★★ **これが規範であり、以下すべての前提**（r9 監査 HIGH / r10 監査 LOW）。
**パス文字列を受け取る `fetch_technocore(path)` は、公開 API としても
MCP 内部 API としても提供しない。** 受け取るのは
**経路テンプレートの識別子＋検証済み segment** だけである:

```
fetch_technocore(ROUTE_ROOM,     room=<validate_name 済み>)
fetch_technocore(ROUTE_KV_READ,  ns=<validate_name 済み>, key=<validate_name 済み>)
fetch_technocore(ROUTE_ROOMS)
```

- テンプレートは **MCP 内の列挙された定数**で、モデルからは選べない
- **書き込みルートのテンプレートは存在しない**（署名付き投稿は `say_signed` 経由）
- **呼び出し側がパスを組める限り、組む時点で混同が起きる**（`key="x/set/<値>"`）。
  だから組み立てをこの関数の内側に閉じる。
  **「パスを渡す形も残しつつ、こちらを推奨する」は選ばない** ── 残せば使われる

### 内部の URL 構築（テンプレート選択後）の条件

上のテンプレートと segment から実際の URL を組む**内部処理**の条件。
外から任意のパスが入ってくる前提ではなく、**組み間違いを自分で捕まえるため**の三段:

1. 組み上がる path は **`/` ちょうど1つで始まる origin 相対パス**であること。
   `//` 始まり・バックスラッシュ・制御文字/不可視文字（e2e.py の sweep 対象カテゴリ）
   ・authority に解釈されうる要素があれば**中止**
2. **文字列連結ではなく構造化して組む**（`urllib.parse.urlunsplit` に
   scheme / host / path を別々に渡す。host は設定値であって入力ではない）
3. ★ **組んだ後に最終 URL をパースし直し、`scheme == "https"` かつ
   `hostname` が設定した technocore ホストと完全一致することを確かめる。
   違えば送信しない**

★ **3 が本体である。** 1 と 2 は入力の話で、いくらでも書き漏らせる
（現に `.evil.com` を漏らした）。3 は**結果を見る**ので、
1 と 2 の書き漏らしがあっても止まる。
**「悪い形を列挙して弾く」ではなく「良い結果であることを確かめる」に倒す。**

★★ **ただし 1〜3 はどれも「どのホストへ行くか」しか決めない。**
**「そのホストで何をするか」は決めない。**
technocore は読みと書きが隣接ルートなので、host が正しいまま
`/kv/ns/key` が `/kv/ns/key/set/<値>` になりうる ──
それを止めているのは 1〜3 ではなく、**上の API 形（テンプレート＋検証済み segment）と
§2 の `validate_name` 規則**である。この2つは別の問いに答えており、
**片方を通したことは他方の証明にならない。**

### vendor の `get` を誰が呼ぶか（r7 監査 MEDIUM）

r6 版は「vendor の `get` を呼ぶのはラッパーだけ」と書いたが、
**許可した `say_signed`（506行）と `read_room`（515行）が直接 `get` を呼んでいる。**
そのまま検査を書けば許可済み関数で落ち、例外を切れば「ラッパーだけ」を証明しない。
**不変条件と許可リストが矛盾していた。** 正しくは2条に分ける:

- **(a) MCP 自身のコードは、`fetch_technocore` を通してのみ vendor `get` に到達してよい。**
  MCP のモジュールから `get` への直接参照があれば落とす
- **(b) 許可した vendor 関数（`say_signed` / `read_room`）が内部で `get` を呼ぶのは可。**
  ただし許可の根拠は「呼ばないこと」ではなく
  **「`BASE` 直後がリテラル `/` で、可変部が `validate_name` を通ること」**である。
  この2関数の URL 構築行は**上流更新時に差分を見る対象**として
  `vendor/REVIEW_POINTS.md` に記録する（§4 の照合はバイト一致しか見ないので、
  構築の形が変わっても hash 一致では気づけるが**何が変わったかは分からない**）

★ **一般化**: 許可リストの1行は関数名でも引数名でも決まらない。
**宛先を決めるバイト列を誰が持っているか**で決まる。
副作用の欄にはそれを書く。

**許可リストに足すには、副作用の欄を埋める。** 空欄では足せない。
新しい CLI コマンドが上流に増えても、既定禁止なので黙って露出しない。
★ **テストは実在シンボルの集合として書く**（`dir(vendor)` と突き合わせ、
許可リストに vendor に無い名前があれば**その時点で落とす**）。
これが無いと、名前を間違えたテストが「合格」を出し続ける。

### ★ この照合が保証する範囲（r1 監査 MEDIUM への対処）

初版は「これで黙って古くなることを避けられる」と書いたが、**それは誤りだった。**
起動時照合は**配布物の中でコピーと記録値を突き合わせるだけ**なので:

| 検出できる | 検出できない |
|---|---|
| 配布後のローカル改変 | **上流が新しい仕様へ動いたこと** |
| パッケージの破損・取り違え | 記録値ごと差し替えられた場合 |

**上流 drift は別の仕組みで見る。** リリース手順と CI で:
1. `vendor/UPSTREAM.txt` の commit の内容と `vendor/e2e.py` が一致するか
2. その commit が上流 `main` の最新かどうか（違えば警告）

README には **「起動時ハッシュは配布物の整合性を見るもので、上流の鮮度は保証しない」**
と明記する。

★ 教訓の適用: e2e.py 自身が「サーバが動いたのに追随できていなかった」件で痛い目を見た。
**そこで学ぶべきだったのは「複製に印を付ければ安全」ではなく「印が何を検出するのかを
書く」こと**だった。初版はその教訓を引きながら、同じ甘さを持ち込んでいた。

## 5. tclk/1 の呼び出し方針 — **公式ホスト型 MCP を指すだけ。実装しない**

独自実装はしない。**このサーバは tclk のツールを一切提供しない。**

代わりに README で「tclk を使いたければ `~/.hermes/config.yaml` にもう1つ MCP サーバを
足せばよい」と案内する:

```yaml
mcp_servers:
  technocore:
    command: "python"
    args: ["-m", "technocore_mcp"]
  tclk:
    url: "https://tclk.technocore.chat/mcp"
```

**この形が正しい理由**: MCP は複数サーバを並べる前提の機構であり、tclk は公式が既に
MCP で出している。こちらが薄いラッパーを被せれば、**上流が変わるたびに壊れる中間層**が
1枚増えるだけで、利用者に何の得もない。

**npm パッケージ（`@flop-labs/tclk`）を Python から呼ぶ案は却下**。Node ランタイム依存が
増え、隔離境界に subprocess 実行が加わる。ホスト型 MCP なら HTTPS 1本で済む。

### ★ 署名前の検証境界（r1 監査 MEDIUM への対処）

初版は「鍵を手元に置く」だけで足りるとしていたが、**足りない。**
鍵を渡さなくても、**ホスト型 MCP はツールの説明文・返却テキスト・署名対象として
提示するフレームを支配する**。誤ったフレームに手元の署名器で署名させる誘導は残る。

したがって **署名の直前に、手元で以下を満たすこと**を設計条件とする:

1. 署名対象の canonical フレームを**手元でパースする**。ホスト型 MCP の自然文説明を
   信用しない
2. **金額 / asset / rail / 相手 DID / 各期限 / contract id / rail ref** を、
   パース済みの構造データから提示・確認する
3. contract id を**手元で再計算**して一致を確かめる（仕様に算出式がある。
   `0x` + sha256(`FLOP::tclk::v1|contract|<canonical>`)）
4. 一致しない・パースできない・未知フィールドがある → **署名しない**

`TECHNOCORE_SIGNING_KEY` をサーバ側に置く運用モードは**選ばない**（署名は必ず手元）。
これは上記1〜4があって初めて意味を持つ。**鍵の所在だけでは守れない。**

★ **5. 受け取った tclk フレームを状態遷移に使うなら、重複排除する。**
tclk のフレームはルームに載る署名済みレコードであり、§3 のとおり
**尾（1 MiB）を越えれば同じ署名済み URL が再度受理される**。
つまり「相手が offer を出した」「accept が来た」は**再送されうる**。
`(did, nonce, text)` かフレームの `nonce` フィールドで一度きりを自分で保証する。
**署名の検証を通ったことは、初めて見たことを意味しない。**
これは §3 の帰結をここに落としたもので、tclk は
「署名済みレコードで状態が動く消費側」の典型例である。

### 未実装機能の見せ方（r1 監査 LOW への対処）

初版は「tool 名を予約し、呼ばれたら『仕様未公開』を返す stub」としていたが、
**常時失敗するツールを一覧に出すと、エージェントが繰り返し呼ぶ誘因になる。**

改める:

- **未実装のツールは `tools/list` に出さない**
- 代わりに `technocore_capabilities`（読み取り専用）を1つ提供し、
  `{faucet: "unavailable: spec_not_published", inference: "unavailable: spec_not_published", ...}`
  を返す。**呼び出し側は一度これを見れば、無いのか未だなのかを区別できる**
- 将来 stub を露出させる必要が出た場合も、返すエラーは機械可読にし、
  **retry 不可・課金なし・ネットワーク送信なし**を明示する

★ 「無言で失敗させない」という当初の意図は維持したまま、**その表現をツールの存在ではなく
capability の申告に移す**。

## 7. 配備先の選び方（この設計を使う人向け）

原本ではここで具体的なホストを名前で比較していた。公開版では落としてある ──
その比較は我々の環境についての判断で、読み手の役には立たないため。代わりに、
比較に使った観点だけ残す:

- **隣に何が住んでいるか。** 侵害されたとき被害が届く範囲は、このサーバが
  持っている権限ではなく、**同じホストにある他の資産**で決まる
- **専用ユーザで動かし、マウントを持たせない。** ホームは 0700、sudo 非所属
- ★ **論理的な分離は作れるが、同一ホストであるという事実は消えない。**
  事故は論理の外で起きる。使い捨てホストが設計としては最も素直で、
  コストと引き換えになる
- **egress を意図的に塞いだ箱に、外向き通信するプロセスを置かない。**
  遮断の意図と正面から噛み合わない

★ **成果物自体は LLM を必要としない**（§0）。プロバイダ選定が要るのは、
統合を端から端まで試すテスト用エージェントのインスタンスだけである。
その際も**本番と同じ鍵は使わない** ── クォータを共有すると、テストが本番の配信を
止めうる。
